Written 2026-11-23 at the end of the prototyping session.

**Status (2026-11-23): milestone 1 built.** All six slices are merged, with the final pass (branch `final`) on top: one end-to-end live run on haiku through the real backend and the page, the app built and launched on the same state. What is left is the author's check in the real window (below).

## How to run

- `(cd app/backend && npm ci)` once, then `app/build.sh` builds `build/Synopia.app`; `open build/Synopia.app` runs it on `~/Library/Application Support/Synopia`.
- `app/dev.sh` runs the backend alone for Chrome (state in `app/.dev-state/`); `app/dev.sh --fake` plays the fake driver over the fixture tree, with no model calls.
- `app/check.sh` runs every check (backend tests, shell type check, page script syntax), one pass or fail line per part. Page checks over headless Chrome: `app/web/dev/cdp/run.sh <dnd|keys|menu|csp|preview>`.
- A test app on its own state: `open --env SYNOPIA_STATE_DIR=/tmp/s --env SYNOPIA_SNAPSHOT=/tmp/s.png build/Synopia.app`; quit it with `pkill -TERM -x Synopia`. `app/README.md` has the same commands.

## Known limits

- The Now line is rewritten 20 s after a turn ends or a background shell, monitor or subagent ends; it still lags a card that is waiting.
- A message draft survives a backend restart while the page stays open (it reconnects), not a page reload: drafts aren't stored.
- On the very first launch for a folder (no `menu-cache.json` entry yet) the header shows the raw model id until the folder's menu arrives, about 1 to 5 s. After that the stored model list names it at once.
- Paths map only the real path of `/tmp` and of home back (`paths.ts`); other links (a project folder reached through a symlink) show their real path.
- Markdown joins single line breaks into one paragraph, as the prototype does: a poem written one line per line reads as a paragraph.
- A task ended by the SDK's `task_notification` between turns is kept in memory only; the JSONL's own notification (written at the next turn) or the process-end mark covers a restart.

1. **Shell. Decided starting point (2026-11-23):** a small native Swift shell (AppKit window, menus, shortcuts) hosting the prototype's web UI in WKWebView, plus a Node backend that runs the Agent SDK.
   - A locally built Swift app launched fine on this machine under Jamf Protect (experiment A, `swiftc`, nothing downloaded). Chrome's `--app` window works too, as a fallback.
   - Electron is out for now: it needs a ~150 MB downloaded runtime that Jamf may block, and adds a second browser engine.
   - Fully native SwiftUI is out: there's no Swift Agent SDK, and the custom UI would be a rewrite.
   - The shell talks to the page through WKScriptMessageHandler / evaluateJavaScript. Native extras (Dock badge, notifications) come later; when they do, the shell should read state from the backend, not the page.
2. **Session ownership.**
   - Adopting a live CLI session needs that process closed first, since there's one writer per session.
   - How Synopia finds open sessions: `~/.claude/sessions` and its own SDK sessions.
   - What the "closed" state means and where it's stored.
3. **Status.**
   - Live state comes from SDK events (undocumented env flag) for Synopia's own sessions, and from the session files for others.
   - "Needs you" is derived from the pending step, not only from the status.
4. **Claude-written content.** Titles, the "Now" line, drift detection, the closing note and grouping suggestions: which model, when they're regenerated, the cost.
5. **Persistence.** The user's layout (groups, order), "reviewed" marks, notes, and per-session model choice.
6. **Answering.** Questions, permissions and plans through `canUseTool`, including notes (`annotations.notes`), "always allow" rules, and `permissionMode: 'default'` despite the user's `auto` setting.
7. **Rendering.** The CLI-like transcript from SDK messages, not from re-reading JSONL, and the diffs from `structuredPatch`.

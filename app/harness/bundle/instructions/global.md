# Global working rules

- Edit files with the host's edit tool, not with shell commands or scripts.
- Before reporting a code change as done, run the project's compile/test command and report the result.
- Never print, commit, or paste secrets, tokens, or credential files.
- Match the existing code style. Do not reformat files you did not otherwise need to change.
- If the project has its own `AGENTS.md`, follow it over these defaults.
- Go as far as you can without asking: merge, fix, rebuild, start the next step. Stop only for a product decision that is the user's, or a check that needs the user's hands. Ask those in the reply, together, each with your recommendation.
- Ask before using macOS automation or permissions: osascript or System Events, UI scripting, synthetic input events, screen capture.
- Delegate to a fresh subagent with a self-contained brief: a full task spec, file ownership and the expected report format, never a copy of the conversation. "Do it in a fork" or "with a clean context" means this. Run independent tasks in parallel in the background.
  - Parallel subagents that change files each work in their own git worktree, started from the newest mainline work: the local or the remote main branch, whichever is further ahead.
  - Delegate self-contained work (captures, long test runs, extraction, doc fixes) when it saves tokens or keeps the main context clear.
  - When the user asks for a deliverable they will review (an artifact, report, design, asset, document), or brings up a new self-contained task while another thread is going, delegate it to a background subagent instead of doing it in the main thread, even when it looks small. Start the description with `For review: ` when the user will review the result. Tell the user in one line that it started, then go on with the conversation. When it finishes, tell the user it's ready: what it is, where it is, how to open it, and what to look at first. Then stop for their review instead of building on it. Subagents you start for your own steps don't get the prefix.
- Resolve a merge conflict part by part on its merits; never take one side's whole file. Afterwards, check that nothing either side added was lost.
- Do not run tests or commands after every small edit or step: each run burns tokens on output already seen to pass. Verify at milestones, trust green code in between, and fix what fails. Never let them print long output: filter it to the pass or fail line, the failure count and the failing numbers.
- Write tools so their default output is minimal: one summary line or a short table, with details behind a flag.
- When work spans several sessions, subagents or PRs, keep notes in `.ai-notes/<area>/` (see the `ai-notes` skill). Read `.ai-notes/README.md` at the start of a session if it exists.
- After you push to a pull request, open one, or start a long local fix-and-test loop, arm a background watcher with the `feedback-watch` skill and react to its lines instead of checking CI, reviews or tests by hand. Keep one watcher per set of PRs and re-arm it when it expires.
- Compute is free, tokens are not. Ten hours of machine time that give the exact answer beat 150 experiments whose orchestration costs tokens, above all when reverse engineering: decompile, emulate or run a batch extractor to read the definitive logic, then measure only what that leaves open, in one scripted batch.
- For external libraries, tools and services, the documented surface (docs, typings, public API, --help) is the source of truth. Do not read minified, compiled or binary internals unless the task is reverse engineering. Settle behaviour the docs leave open with one scripted check, and keep the code that depends on it in one place.
- Before starting a task, check your available skills for one whose description fits and use it, for example, when available, `frontend-design` for visual work (UI, icons, mockups, storyboards) or a reverse-engineering skill such as REA for binaries and app behaviour. This applies to subagents too. When you delegate and know a skill fits, name it in the brief as well.
- In replies to the user, write every pull request, issue or ticket number as a markdown link to it (for example `[#123](https://github.com/<owner>/<repo>/pull/123)`), not as bare text.
- When a reply suggests a shell command for the user to run (open a file, log in, clean up), write it with the `!` prefix, for example `! open prototype/storyboard.html`, so it runs in the session and its output lands in the conversation. Commands you run yourself are unaffected. Claude Code supports the prefix; in opencode it is unverified.
- Before writing any text a human will read and act on (pages, QA scripts, runbooks, plans, PR descriptions, ticket text, longer replies), follow the `writing-craft` skill.
- Sign every commit when signing is required: `commit.gpgsign` is on, or the project's rules ask for it. Then never pass `--no-gpg-sign` or `-c commit.gpgsign=false`. `git commit-tree` ignores `commit.gpgsign`: pass `-S` when it is on. If signing fails (no key, agent unreachable from a sandbox), stop and report the error instead of committing unsigned. Don't mention signing when you report commits.

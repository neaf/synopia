Every shell command, one way: a preview in the transcript, the rest in the shell view

How Synopia shows each shell command in a session, whoever starts it and however long it runs. The page compares the real choices and recommends one design. Every frame uses the app's own CSS and markup; only the run row, the sign for who started a run and the waiting card are new. Every session, folder, command and output here is invented.

Recommended

  • Every run is one row of the same shape. The command, its last 3 lines of output, and one state line with a status mark: Running, Waits for input, Finished, Exit code 1, Stopped. The row never grows and never takes input.
  • The row is a link. A click anywhere on it opens the shell view: the whole output, input and stop. Nothing expands in place.
  • A run gets a panel card after 3 s. Any run still going after 3 s gets a card, and so does a run that waits for input. That covers Claude's foreground and background Bash, monitors, your ! commands and the credential refresh. ! open . stays a single band with no card.
  • Claude's command line starts with a grey $. In the gutter under the step's dot, in the column of your band's !, as on the permission card; no band, no fill. One mark per gutter line.
  • The sign says who started it. Your runs keep the ! band in the transcript, and their cards and Past lines put a pink ! before the command. Claude's runs keep the ● tool line. Synopia's refresh shows the lock.
  • Waiting for input means needs you. The run shows the red pause mark in its row, its card turns red, and the sidebar reads "Needs you, a command waits for input".
  • Input and stop happen in the shell view only. Input goes in the box's place, on a ! band. Esc, Esc there stops that run, Claude's background shells and monitors too.
  • The credential refresh is a run like any other. The dock keeps one line about the sign-in, with the run's preview under it. Its output and input move to its shell view.

Requirement changes

  • R5.6, FR-VIEW-05: a Bash or Monitor step is a run row: the command on one line, the last 3 lines in the output panel, the state line. A click opens the shell view. In-place expansion and "Show all N lines" go for shell steps; they stay for other tools. The command line of Claude's step, and of its shell view, has a grey $ in the gutter (the permission card's .ps style), the dot staying on the step line.
  • R5.13, FR-BOX-03: your ! row is the same run row (3 lines, was 5 while running and 20 once ended). The input line under the row goes, and so does "Esc, Esc to end it". A run that ends at once with no output shows its band alone; "No output" goes.
  • R5.5, FR-VIEW-03: a click on "Working Bash(…)" opens that run's shell view. Your own runs are never on the Working line.
  • R7.1, FR-BG-01: a card for every run still going after 3 s, or waiting for input; one ended in under 3 s gets none. The pink ! and the lock before the name; a waiting card is red with the pause mark.
  • R7.2, FR-BG-05: the shell view opens for every run, Claude's foreground Bash and finished runs included. Input goes in the box's place; Esc, Esc stops the run.
  • R9.4, Q11, FR-BG-06: stopping a background shell or monitor is designed: Esc, Esc in its shell view (stopTask). In the main view, Esc, Esc stops only the turn. The Stop row stays dropped.
  • R8.2, FR-STAT-02: New status "Needs you, a command waits for input". The sign-in expired line loses its output, field and Cancel to the refresh's run.
  • R4.2: New sidebar sub-line for a run of yours that waits for input.

Open questions

  1. How does Synopia know a command waits? No exact signal was found: in one check, macOS ps -o wchan printed - for a blocked command. The proposal: 1 s without output when the last line ends without a newline (a prompt), or 10 s without output. One scripted batch over ten common prompts would settle it.
  2. Should Esc, Esc in the main view still stop your running ! command when no turn runs? The proposal: no, so stopping has one place.
  3. Is 3 s right? Lower brings cards for most git calls; higher leaves a 5 s build without a card.
  4. Live output for Claude's foreground Bash. Not checked: whether its task's output file exists from task_started and how the CLI names it. Synopia never builds the path, so today it waits for the result.
  5. One refresh for several sessions. Should its card show in each session of the folder, as drawn, or only in the session that hit the expiry?

1. The row: one shape for every run, in every state

The same five states for a run Claude started (left) and one you started (right). The row has the command, at most 3 lines of output, and the state line with the panel's status marks. Today a Claude step is one line that expands to 20 lines, and a ! row shows 5 lines while it runs and 20 once it ends.

The command line: a grey $ for Claude's, the pink ! band for yours

Proposed by the author after the first review. Claude's command line gets a grey $ in the gutter, under the step's dot and in the column of your band's !, as the permission card shows a command. It has no band and no fill, so the pink ! band stays the sign for yours. Each gutter line has one mark: the dot on the step line, $ on the command line.

The recommended flow

5. Claude's foreground bin/rspec

Claude runs the suite and waits for it. The Agent SDK reports only a foreground step's elapsed time, so its output shows when it finishes. The row says so in place of the 3 lines. It gets its card at 3 s, like any run.

6. Claude's background dev server

Claude starts npm run dev with run_in_background and goes on. The row is the same shape; its state line says "in the background". Its output comes live from its output file.

7. A monitor watching CI

Claude watches CI on the branch with the Monitor tool. Each line is an event Claude hears. The row shows the last 3 events and their count; the monitor ends at its deadline or when CI is done.

8. b, b: a foreground Bash moved to the background

Claude's end-to-end tests run in the foreground for 1 minute, and you want to talk to Claude meanwhile. Once the run moves, its output file is named, so its 3 lines appear in the row.

9. A subagent's background shell

The subagent "Build image thumbnails" starts bin/resize --all in the background. Its run lives in the subagent's transcript, and its card hangs under the subagent's card, as today. The main transcript and the sidebar count don't show it.

10. A failing command

Claude runs the upload specs and one test fails with exit code 1 after 41 s. The last 3 lines are what went wrong; stderr keeps its red text and 1px rule.

11. The credential refresh

A request fails on expired credentials. Synopia runs the folder's refresh command, bin/aws-login, in a terminal, and the command asks for an MFA code. Today the dock shows the command's output live, a field that types into it, and Cancel.

The recommended flow

12. Stopping a run

Stopping happens where the whole run is: in its shell view, with the key that stops a turn. The same prompt works for your ! run (SIGTERM to its process group, then SIGKILL after 3 s), Claude's background shell or monitor (stopTask), and the refresh. For Claude's foreground Bash the view asks "Interrupt?", since the step is the turn.

Edge cases

Rejected

  • An input field in the transcript row. The author's ask: the transcript is a preview, and a field in it is a second place to type to a command.
  • A Stop button on the row or the card. The panel would move when a card's buttons show, which is why the Stop row was dropped; the key in the shell view stops without a button.
  • A separate "Shells" section in the panel. The panel's rejected list already has sections per kind; shells stay in the one tree.
  • A pink card for your runs. Colour alone, and pink means bash mode in the box; the ! sign carries it by shape.
  • Live output for Claude's foreground Bash read from a guessed file path. Synopia takes only paths the transcript names. Open question 4 asks for the one check.
  • Counting your runs in the sidebar's "1 shell or monitor running". That line is Claude's work; only a run of yours that needs you reaches the sidebar.

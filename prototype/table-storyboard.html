Tables in Claude's replies

Claude often answers with a markdown table. Today short cells such as ~44 ms break onto two lines, so the rows are uneven and twice as tall as they need to be, numbers sit on the left, and nothing separates one row from the next. This page tries four fixes on the same table, in the transcript's real mono text, at two widths: a reply about 1000px wide and a narrow one of 640px.

Each variant has three rows of frames: the endpoint table, a wide table with 10 columns, and a table with a long text column. Under each frame are the table's height and how many number and short cells broke onto two lines.

TodayThe app's CSS as it is: 12px, 1px padding, a rule under the header.
A: fixes onlyThe same 12px. Short cells keep to one line, numbers align right, the long text column takes the slack.
B: A, smaller, ruled RecommendedThe table at 11px, today's 1px row padding, a 1px rule between rows.
C: B, quiet header, fillThe header in regular grey, every second row on a light fill in place of the rules.
D: B, lighter units, stacksUnits a step lighter than their numbers. A table that doesn't fit becomes one record per row.

How A to D fit a table. The renderer marks each column once, from its cells: numbers (every cell a number with an optional unit, such as ~44 ms or 418k + 386k), long text (a cell over 44 characters), or short. Then it fits the table in up to three steps and stops at the first that fits: 1. only the long text wraps; 2. the first column may wrap too, but never inside its code; 3. the table scrolls sideways inside its own box (D stacks it instead). It runs again when the panel is resized.

B in dark mode

The row rules are the dark --line-2 (#434B57) on the panel (#333A44): visible, but quieter than the header rule.

Why B

B fixes what made the table hard to read, and changes little else. Most of the height today comes from short cells breaking, and A already fixes that: every row is one line high at 1000px. The step from 12px to 11px gives about 8% more room, which in the narrow reply keeps the first column on one line longer. The 1px rules let your eye follow a row across a wide gap between the first column and the verdict.

Why not C or D. C's fill is the only shaded block in the transcript besides your own message bands and code blocks, so a table starts to look like one of those. D's stacked records are a second way to show the same table, which breaks "one way to do each thing", and you lose the column you compare by; horizontal scroll keeps the table a table. D's lighter units are worth a second look on their own (question 4).

Open questions

  1. Should code blocks and inline code shrink to 11px too, or does only the table change? Drawn: only the table, with its inline code at the table's own size.
  2. When a markdown table states its alignment (|---:|), should that win over the detected one? Today the renderer ignores the colons. Drawn: detection only.
  3. How should a column of mixed numbers and text align, such as 65 ms, n/a and timed out? Drawn: one cell that isn't a number makes the whole column text, aligned left.
  4. Should units be a step lighter than their numbers, as in D, in B as well?
  5. When the table scrolls sideways, should the first column stay in place, so you always see which row you are reading?

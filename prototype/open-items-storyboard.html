What waits on you, kept by AI: open items across turns and sessions

How a long session keeps its loose ends: the decisions Claude needs, the tasks only you can do, what Claude will re-check later, and the proposals that go ahead unless you object. The page compares the real choices and recommends one design: a skill and a file as the base, then Synopia's keeper, panel and list on top. Its text companion is prototype/open-items-design.md. Every frame uses the app's own CSS and markup; only the open items, the sidebar line and the Waiting on you list are new. Every session, folder, pull request, person and command here is invented.

Recommended

  • You never keep the list. AI finds the items in the conversation, Claude's and yours ("I'll review it tonight", "remind me"), and closes them when they're answered or done.
  • The base is a skill and a file. The open-items skill in agent-harness, and .ai-notes/<area>/open-items.md per area. Every turn the agent closes what you answered, opens what its reply leaves open, re-checks due follow-ups, and prints the reply's "Waiting on you" block from the file. It works in the CLI.
  • Ids are short and stable. Y1, Y2 wait on you; A1, A2 wait on Claude. The same id in the CLI, in Synopia and after a handoff.
  • Prose answers just work. Quote a line and write "Run it", or write "Y1 run it, Y3 later". An answer that could mean two items gets a one-line question, never a guess.
  • Synopia's keeper reads every exchange too. A one-shot model call after you send and after each turn returns typed changes. Each change must quote the exchange word for word, or it's dropped. It catches what the agent forgot, and keeps a list for sessions with no skill.
  • Synopia owns one list per ledger and writes the file back. Your corrections, the agent's records (the open_items tool or its file edits) and the keeper's changes are its inputs, applied in that order.
  • The panel shows it. "Waiting on you" and "Claude will check" in the background panel; "Closed this turn" with Undo. A solid id box means Claude recorded it, a dashed one that Synopia found it.
  • Buttons only write prose. An option writes Y1 Run it into the box. Enter sends, as for any message.
  • Your turn stays your turn. A sidebar line says "○ 4 waiting on you"; Needs you stays for the cards that block.
  • Subagents work on items but never write the list. A brief names the ids a subagent owns, shown under its card; its report says which it closed, and its questions become your items. A finished For review: subagent opens a review item, and To review shows those items.
  • One list across sessions: w opens every open item of every session, like the Open list.

Open questions

  1. Do inferred changes apply at once (marked, with Undo), or wait for the agent's confirmation next turn? Proposal: at once.
  2. May Synopia write the ledger file in your repo, so the CLI and a handoff carry the keeper's finds? Proposal: yes, between turns, only for a file the agent created.
  3. The keeper's model. Proposal: a stronger model than the titles' haiku, since a wrong item costs attention and calls are free. Not checked: one scripted batch of 50 invented exchanges would show the gap.
  4. Should Synopia wake an idle session when a trigger it can check fires? Proposal: not yet; the agent's own watcher starts the turn.

Recommended flow

2. Answering one item in prose

You quote Y1's line from the reply and write "Run it", as you would today. No id, no button. The keeper marks it answered the moment you send; Claude runs the fix and closes it.

3. Several in one message, by id

Ids are the shortcut for many at once. You click "Keep them" on Y4, which writes Y4 Keep them into the box, then type two more lines yourself. One message, three items.

4. A follow-up whose trigger fires later

A1 says "after the M2 stack merges: re-check #820". Claude armed a watcher on #812 to #815 when it recorded A1. Two hours later, at 4:40 PM, the last one merges. The watcher's line starts Claude's turn; nobody has to remember.

5. A default that goes ahead

Y3 proposes an order for marking #812 to #815 ready and goes ahead when CI is green on all four. You answer other items and don't object. CI turns green at 2:31 PM.

6. The keeper catches what the agent didn't

Three ways the list stays right without you: an item the agent forgot to record, a task of yours that the work shows done, and a follow-up that went stale. Each change is marked "by Synopia" and can be undone for one turn.

7. A wrong guess, corrected without curating

The keeper took a question Claude answered itself as a decision for you, and later read your "go" as closing the wrong item. Each fix is one key or one sentence.

8. A handoff carries the ledger

The session is long; you type /handoff. The handoff file lists open-items.md first, the new session reads it, and every id stays as it was.

9. Everything waiting on you, across sessions

Three sessions open, 7 items waiting on you in them. You want to clear them in one sitting, without opening each session to find out.

10. Subagents work on items, and never write the list

Your decisions of 2026-11-26. You answer Y5 "Main's", and Claude hands the rebase to a subagent; a second one drafts the receipt email copy for your review. Only Claude and Synopia write the list: a subagent's brief names the items it owns, and its report says which it closed and what it needs from you.

The same frames in the dark theme: the sidebar stays the darkest surface, ids keep their solid and dashed boxes, and the list uses the selection tint.

Edge cases

Rejected

  • An "Add item" button or field. You asked never to add items by hand; saying it in the session opens it.
  • Synopia's code reading items out of prose (a regex for "Waiting on you"). It breaks on the next wording; only a model reads prose, and code checks its typed output.
  • The ledger built on Claude Code's task list. The task tools are off by default on newer models, the list lives in ~/.claude/tasks/ outside the repo, and only Claude Code reads it.
  • The rules as a section of ai-notes. It isn't loaded every turn, and sessions without a notes area would get no rules.
  • Answer buttons that send at once. Several answers would be several messages and several turns; writing into the box keeps one way to send.
  • Needs you while a decision is open. In a long session something nearly always waits on you; red would stop meaning blocked.
  • The file as the one owner, with the keeper writing it too. Two writers race on one file mid-turn, and Synopia's own facts (found by, undone, not an item) would live in your repo.
  • Two lists side by side, the agent's and the keeper's. The same item shows twice and you end up merging them.
  • One id prefix per kind (D1, T1, F1, P1). You only need to know whether it waits on you; four prefixes are four things to learn.
  • Synopia evaluating triggers itself (polling GitHub). It would be a second watcher beside feedback-watch; the agent's watcher already starts the turn.

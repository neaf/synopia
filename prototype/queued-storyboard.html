Queued messages: one veil

A message you send while Claude works is drawn exactly like one it already has. One veil, the panel colour at half strength, lies over the first waiting message and everything under it. Each time Claude takes a message, the veil's top moves down past it, and nothing else moves. v3 is the current proposal; v2 and v1 follow for comparison.

v3: one veil, and bands that join

Where the build is: queued messages are drawn exactly like posted ones, and one veil, the panel colour at 50%, covers from the top of the first queued message to the bottom of the transcript. It takes no space and has no edge or label. The problem: each ❯ message is its own grey band with a white gap above and below. Several in a row make a zebra, and a white veil over a white panel only dims the text, so the block never reads as one. Posted messages in a row have the same zebra.

The numbers at the right are each band's top, in pixels from the top of the transcript. The blue tick is the veil's top.

2 to 4. Three fixes

The same transcript in each. A and B change posted and queued messages alike, since they must look the same; C changes only the veil.

Recommended: B, one band with a 1px line between messages. Joined, the messages are one grey surface, so the veil has something to dim: the block reads as one lighter unit, and its top is a visible change of tone instead of a lighter word. The line is drawn inside the band's top, so it adds no height, and the left edge stays one unbroken 2.5px rule. v2: a split that takes no space

What changed since v1, after your review:
  1. The split takes no space. There is no label row and no line between messages: the block is painted over the log from the split down to its end, so moving the split moves nothing.
  2. The waiting messages are dimmed as one block, not one by one. A taken message leaves the block at its top; the bands never change size or markup.
  3. The count and the f f hint move to the message box, as its placeholder: "4 waiting. f f sends them now." That is where f f acts, and it costs the log nothing.

The numbers at the right of each frame are the top of each band, in pixels from the top of the transcript. The blue tick is the split.

2. Four messages waiting: two treatments for the block

The same transcript in both; only the block's treatment differs.

Recommended: A, the overlay with a 1px top edge. The edge gives the split a shape, so it does not rest on contrast alone, and it is a 1px line drawn inside the block's top, so it takes no space. The overlay is one surface: the first f tints it and rings it in one move, and in dark mode it dims toward the panel colour rather than toward a transparent grey. B, one opacity, is the calmest, but on a bright screen the split is only a change in contrast.

3. Claude takes the first at its next step

The only change is the block's top edge, which moves from above the first message to above the second. Every band keeps its y-position: the numbers at the right are the same in both frames. The live line stays where it is and only its words change. When Claude's next step writes its lines, they land under the message it took and push the whole block down at once, as any new output does.

4 and 5. f, then f: send all now

The first f asks in the message box and marks the waiting block as one unit, with the selection tint and the 1px blue ring that b b uses. The second f sends them all: the block goes away, all four read as sent, and nothing moves.

Open questions

v2 settles one question from v1: the f f hint and the count go in the message box, not the log.

  1. After Claude takes a message, the live line stays above it until Claude's next step writes. Is that acceptable for those few seconds, or should the live line wait below the block?
  2. Esc, Esc interrupts the turn. Do all waiting messages still go back to the message box, joined in the order sent, or do they stay queued for the next turn? Today they go back to the box.
  3. What does f f do when nothing waits: nothing, or the box says "Nothing is waiting" for a moment?
  4. Does Ctrl+Enter in the message box do the same, as in the Claude Code CLI? If so, does it skip the question, since you are already typing?
  5. "Now" depends on what the Agent SDK can do. If it can only hand the messages over at the next step anyway, is f f still worth a key, or should "now" mean stop the current step?
  6. The placeholder shows only while the box is empty. Once you start typing, is it fine that the count is gone, or should the live line also say "4 waiting"?
  7. Can you take back or edit one waiting message, or only all of them at once with Esc, Esc?
  8. If Claude takes all four at the same step, does the edge move to the end in one move, exactly as after f f?

v1, for comparison

The first version: a label row marks the split and each message is dimmed on its own.

1. One message waiting

Your message sits below the live line as the posted band, dimmed whole. The line above it is the split point. Nothing on it moves: it waits, it does not run. The live line keeps its turning mark.

2. Four messages waiting: where the split point goes

Four messages sent while the export specs run. The same four in each variant; only the marker of the split differs.

Recommended: A, the cursor line. It marks the split in one place, between the live line and the first waiting message, so it reads as a cursor that moves down, and the count is where the eye lands after the live line. B changes the ❯ on every waiting message, so they no longer look exactly like sent ones, and it gives no count. C leaves the split to the dimming alone, which is contrast only and easy to miss on a bright screen, and its count sits at the far end, away from the split.

3. Claude takes the first at its next step

The tests finish and Claude reads your first message before its next step. The cursor moves down one message: that message turns to full strength in place, the live line steps below it, and the count drops to 3. No copy appears and nothing jumps.

4. f, f: send all now

In normal mode, the first f asks in the message box and marks what would go, the way the first b marks the steps it would send to the background. The second f sends them. Any other key keeps them queued.

5. Dark mode

Frames 2A and 4 on the dark palette. The waiting bands dim toward the panel, and the mark uses the dark selection tint with the bright blue ring.
